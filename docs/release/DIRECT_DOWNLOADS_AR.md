# حالة التنزيل المباشر وخطوات الإتاحة

## الحالة الحالية

- صفحة `/download` تعرض Windows 10/11 وMac Intel وApple Silicon وAndroid وiPhone/iPad.
- الهواتف تستخدم `/install#installation-steps` لتثبيت PWA. لا APK ولا App Store في هذا الإصدار.
- روابط ملفات سطح المكتب مغلقة افتراضياً. نجاح البناء أو وضع URL في متغير بيئة لا يفتح التنزيل.
- `releases/approved-installers.json` فارغ عمداً حتى توثيق اختبار الأجهزة الفعلية.
- R2: bucket `arzdesk-desktop-releases`، بلا وصول عام أو custom domain عند المراجعة. لا تفعّل الوصول العام إلى ملفات تجريبية.
- النشر الذي روجع على `arzdesk-sage.vercel.app` كان يعيد 404 لصفحة `/download`، و200 لصفحة `/install`. يجب التحقق مرة ثانية بعد نشر التعديل.

## فحوص الأجهزة المطلوبة

يجب تجربة نفس الملف الذي سيُتاح، على Windows 10 وWindows 11، وعلى Mac Intel وApple Silicon كل بمعماريته. استخدم حساب نظام أو ملف اختبار مستقل، ولا تستعمل Workspaces حقيقية للاختبار.

1. سجّل اسم الملف، بصمته، commit المصدر، إصدار النظام، وتاريخ التجربة.
2. ثبّته من EXE أو DMG الفعلي، لا تشغّل كود المصدر فقط.
3. افصل الإنترنت، وافتح التطبيق، وأنشئ مساحة اختبار وعميلًا ومشروعًا ومهمة، ثم عدّل الحالة والاسم.
4. أغلق التطبيق بالكامل وافتحه مجدداً وتأكد من بقاء السجلات.
5. صدّر backup واستورده؛ تأكد من بقاء النسخة الأصلية وإضافة نسخة صحيحة. لا ترسل ملفات تحتوي بيانات حقيقية.
6. جرّب ترقية نسخة اختبار قديمة إلى المرشح الجديد بنفس ملف التطبيق؛ تحقق من بقاء بيانات الاختبار. لا تمسح بيانات التطبيق لتجاوز خطأ.
7. سجّل سلوك التوقيع وSmartScreen أو Gatekeeper كما ظهر. لا نعتبر الفحص الآلي اعتماداً لتجربة التحميل الحقيقية أو notarization.

## حماية بيانات المستخدم

لم يتغير اسم قاعدة IndexedDB `arzdesk-device-v1` أو schema أو origin `arzdesk://local` أو app ID أو مسار البيانات الإنتاجي. NSIS يضبط `deleteAppDataOnUninstall:false`. فحوص Electron ترفض العمل دون مسار اختبار مطلق يبدأ اسمه بـ `arzdesk-qa-`. ملفات الموقع والمتصفح تبقى مستقلة، والنقل يتم بنسخة احتياطية. لا تغيّر أصل التخزين بين نسخ التطبيق.

## ربط الروابط بعد نجاح الفحص

1. أضف سجلاً حقيقياً في `releases/approved-installers.json` حسب `src/lib/desktop-releases.ts`: platform وversion وsourceCommit وfileName وsha256 وbytes، وphysicalTests مؤرخة تتضمن evidence وخمس checks ناجحة. Windows يحتاج سجلي windows-10 وwindows-11؛ كل DMG يحتاج سجل معماريته. لا تحول نتيجة CI إلى سجل اختبار جهاز فعلي.
2. احتفظ بالمرشحين غير المعتمدين في bucket خاص منفصل. استخدم bucket التنزيل العام للملفات المعتمدة فقط.
3. ارفع الملف المطابق للبصمة إلى:
   `releases/<version>/<sha256>/<fileName>`
4. اضبط Content-Type حسب الملف وContent-Disposition إلى `attachment; filename="<fileName>"`. لا تستبدل كائنًا قديمًا ببصمة مختلفة.
5. اربط نطاق R2 رسمي بعد مراجعة DNS، أو استخدم نطاق R2 المسموح الموجود في الكود للاختبار. `downloads.arzcore.com` اسم مدعوم بالكود فقط؛ ليس تأكيداً بأنه مربوط حالياً. لا تغيّر DNS الشركة أو أي مشروع آخر دون حاجة وتحقق.
6. اضبط `ARZDESK_RELEASES_BASE_URL` في Vercel إلى HTTPS origin المربوط فعلاً. المتغير وحده لا يفعّل التنزيل، وGitHub والنطاقات غير المسموحة مرفوضة.
7. شغّل `node --import tsx scripts/verify-installer-downloads.ts` في بيئة فيها المتغير. ينزّل الملف من المضيف النهائي ويقارن العدد والبصمة، ويرفض التحويلات وغياب attachment filename. لا يلزم كشف أي مفاتيح في السجل.
8. بعد نشر السجل والمتغير المراجعين، تصبح الروابط العامة:
   - `/download/windows`
   - `/download/mac-intel`
   - `/download/mac-arm64`
     قبل الاعتماد ترجع هذه الروابط 503 بلا Location. أزرار صفحة التحميل لا ترسل المستخدم إلى GitHub.

إعداد رفع آلي إلى R2، عند الحاجة، يجب أن يستخدم سرّاً محدوداً بهذا bucket في environment محمي. لا تضف مفاتيح إلى المستودع أو صفحات الموقع أو مخرجات الاختبار.
